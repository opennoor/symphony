# Symphony

Symphony is the sole authority for topology, delegation, lifecycle, reassessment, and completion. Keep the root thin.

**Invocation:** Codex uses `$symphony:symphony ...`; Claude Code uses `/symphony:<command>`. Codex does not support `/symphony:*`.

**Assessor boost:** Codex uses `$symphony:symphony boost [xhigh|max|ultra|off]`; Claude uses `/symphony:boost [xhigh|max|off]`. With no argument each requests its highest native level. This changes only subsequent assessors in the current project/provider/session. `off` or `reset` restores normal high assessment. Unsupported provider or account/model efforts are rejected without changing the preference. Use the exact requested/effective native model and effort reported by the hook or status: Claude selects the packaged assessor agent; Codex passes model and reasoning effort explicitly with `fork_turns="none"`. Worker/lead matrix routes, consent, and Fable access/billing opt-in remain unchanged.

## Root loop

For a control-only invocation, execute or reconcile the control at the root and report its result. Do not spawn a fast lead, assessor, lead or worker for an enable, status, version or other control itself. If the hook already applied the control, relay that completed result. An accompanying task follows the task-routing steps below; an enabled plain objective follows managed routing below and is never executed or completed by the root itself.

**Optional diagnostics:** A hook may offer a public issue containing sanitized recovery counters. Follow [diagnostic sharing](references/diagnostic-sharing.md); ask once without pausing work and publish only after actual scoped user approval. Do not send private recovery records or raw logs.

1. **Check activation.** On Codex, from the project directory run the activation-check command supplied by the hook, which pins the absolute interpreter already running that hook. Keep its digest check and original loaded root arguments. If an older hook supplies only a bare interpreter name, replace that executable with the absolute path of a verified working Python 3.10+; preserve the checker arguments. If no command was supplied, use a verified absolute Python path with `-I "<loaded plugin root>/scripts/check_activation.py"`. Use the plugin root shown in this skill's loaded path. A newly loaded checker can accept this session's older heartbeat after an update only when its retained runtime passes the content digest check. If an update removed the loaded root, use the verified launcher command supplied by the hook, including its original loaded root and `--check-activation`; the heartbeat must also match that retained runtime. Use its retained root for vanished Symphony reference files. Its read-only result checks `CODEX_SESSION_ID`, project, plugin version/root, hook schema, and observation time. A missing dedicated tool is not evidence of a missing heartbeat. Call a run guarded only on a matching result. If verification is pending, explain the native recovery step once and offer an explicitly unguarded one-shot route. Read [provider activation](references/provider-activation.md) for installation, trust, reload, policy, or fault branches.
2. **Clarify at the root.** Agents cannot ask the user anything. When intent or design needs clarification, use a currently callable and compatible brainstorming skill (for example Superpowers `brainstorming`), or make a concise brief and ask only unresolved material questions. Relay the agreed outcome, constraints, assumptions, and success criteria in full. User-facing finishing steps after the lead returns also stay at the root.
3. **Route.** Treat controls as inert. For routine or plausibly mechanical tasks, the root MUST attempt the capable/medium fast lead when offered; do not conservatively bypass it for assessment. Relay the whole request and acceptance checks to that lead. Substantive implementation, diagnosis, design, or review uses an independent assessor directly. An explicit boost or unavailable fast floor also uses the assessor. The root never executes project work. On Codex, use the `symphony_lead_fast_<model>_<effort>` task name offered by the hook, adding a unique underscore suffix if occupied. On Claude, include `SYMPHONY_FAST_ROUTE: lead` in the packaged lead prompt. Use routine read-only inspection of repository state, tools, and native UI to establish the mechanical steps. An objective need not prescribe every command. When confident about the bounded intent, authorized scope, available tools, and concrete verification, execute the full task directly at the selected capable model/medium effort. Examples include git branch/merge cleanup, simple shell commands, and known browser/computer steps. Authorization to delete a merged branch does not by itself create material risk. A clear authorized fast-forward or clean merge remains routine when all commits are preserved and the result can be verified. Verify that every requested result is complete, correct, and accurate before success. Escalate only when actual uncertainty, ambiguity, conflicts, risk of losing unmerged work, unsafe tools, material risk, design or product judgment, or substantive implementation, diagnosis, or review requires it. Routine discovery is not itself an escalation reason. If such a condition appears, pause further changes, report the evidence and any completed steps, and return exactly one `SYMPHONY_FAST_DECISION: escalate` without a completion outcome; the root then requests exactly one independent assessor for the full task. Do not spawn workers, consultants, assessors, or any other descendants. On verified success, return exactly one `SYMPHONY_FAST_DECISION: eligible` line and one valid `SYMPHONY_OUTCOME: {"status":"completed"}` line. A resumed fast turn only reconciles the same bounded task; a new substantive objective requires fresh assessment. Wait for native escalation before launching the independent strongest/high assessor, then follow its matrix-selected route. Missing, failed, interrupted, or misnamed fast results remain recoverable. A prompt alone opens nothing; the first managed spawn opens the run. Every spawn follows [role contracts](references/role-contracts.md).
4. **Resolve.** Use the fixed matrix and the freshest available model-capability snapshot. For optional practices, read [capability routing](references/capability-routing.md): select only an exact skill or tool advertised and usable in this session, read its instructions, and check compatibility with the packet. A cache path or prior session is not availability evidence. Use the listed native practice for an absent, disabled, failed, or incompatible capability. Name applicable practices and acceptance evidence in the lead packet. Aggregate material missing-capability advice into one concise notice when useful; do not delay the route.
5. **Delegate.** Announce the route, spawn and register one lead with an explicit model and effort, relay the bounded packet, then wait through the host's wait/result primitive. The matrix fixes execution topology; the assessor's topology is advisory. Assessed small substantive work needs one worker; medium work uses bounded worker packets. The lead coordinates, integrates, and verifies results. On Claude Code agents run in the background: end the turn after a spawn and the host wakes the root with the result; never poll with Bash, sleep, Monitor, or the agent's output file. Name each assessed lead, assessor, worker, or consultant `symphony_<role>_<model>_<effort>` when the host supports names, appending a unique underscore suffix if occupied; fast leads keep their fast prefix. Announce `Delegating: <role> [<model>/<effort>] — <identity> — <objective>` from observed spawn facts. Repository inspection, implementation, specialist judgment, integration, and verification belong below the root.
6. **Reconcile.** Record host-observed lifecycle facts. Archived followup only completes or reconciles the same bounded task; retain its valid child evidence. Every new objective starts a fresh managed scope and follows step 3; substantive work needs fresh assessment, and previous-task workers cannot satisfy it. Judge this semantic boundary from the full objective, not keywords. An archived fast lead that returns `escalate` needs an independent assessment, never completion under its old direct route. Preserve active ownership and replace a lead only through a safe recorded transition. Reuse returned evidence. For a retryable Codex lead or specific missing work/evidence from an idle completed Codex child, use `followup_task` with the exact underscore-separated `task_name` passed to `spawn_agent`; a `/root/` path or agent UUID is not a valid target. `send_message` only queues a message and does not wake an idle child. Use `wait_agent` only while agent work is active, with `timeout_ms` `300000`; it returns as soon as a child finishes, so fewer, longer waits replace repeated short polls. Replace a lead only after the host confirms it is unavailable.
7. **Complete.** Return the lead's integrated outcome only after it has returned and no tracked work remains active. Keep final summaries concise and proportional to the evidence. Check factual claims against the requirements, inspected artifacts, and fresh results; describe only coverage actually exercised. Omit resolved internal wait and recovery narration; disclose unresolved errors and missing checks. Check the lead's phase evidence and fresh verification; disclose missing checks or scoped exceptions instead of claiming verified success. On Codex, finish the root turn so its native Stop hook can check and archive the run; writing `$symphony:symphony stop` inside an assistant turn does not submit a new user prompt. On Claude, invoke normal `/symphony:stop` in this session. A `completing` run is waiting for that finalization; do not poll it for `completed` or follow up or replace a completed lead solely because it remains `completing`. The normal Stop guard checks current ownership, pending events, and native turn freshness before archiving. If it blocks, reconcile the stated unfinished work and retry normal Stop. Report a run as completed only when durable status confirms it; otherwise report the work and pending checks without claiming lifecycle completion. Keep `SYMPHONY_ASSESSMENT`, `SYMPHONY_ROUTE`, `SYMPHONY_DECISION`, `SYMPHONY_FAST_ROUTE`, `SYMPHONY_FAST_DECISION`, and `SYMPHONY_OUTCOME` markers out of user-facing answers. A host stop is blocked at most once per turn; a repeated stop releases the turn while preserving unfinished work for later reconciliation. It does not prove that agents ended or abandon the run. Only an explicit force stop archives unresolved work. Report only host-observed model, effort, lifecycle, token, and duration facts; omit unavailable metrics. Skill use and practice evidence are agent-reported unless the host exposes a matching event.

Hook task reminders may be clipped. The full original request or assigned packet governs; relay every task part and acceptance check.

Worker and consultant purpose is `substantive` for task work (including a requested review deliverable), or `independent_review` for separate verification only. Claude packets declare `purpose: <purpose>`. Codex names append `__<purpose>` before any unique underscore suffix. Purpose is bound to the original native launch; use a fresh child to change it. Independent review findings cannot replace substantive work.

On Claude Code, model and effort come from the packaged `symphony-<role>-<model>-<effort>` agent type; never use a generic Agent because its call cannot pin effort. On Codex, pass model and reasoning effort explicitly and use the equivalent underscore-separated task name.
