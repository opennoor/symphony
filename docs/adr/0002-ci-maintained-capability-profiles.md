# Capability profiles are built by CI, not discovered at runtime

The 1.0.0 design promised runtime capability resolution: live provider capabilities, then a cached snapshot, then a shipped fallback, refreshed every 24 hours. No component could perform that refresh. Hooks get no model inventory from either host, neither CLI exposes a way to list models, and the thin-root boundary forbids the root from doing capability research, so every route resolved through the shipped fallback while the persisted snapshot field stayed empty. From 1.1.0 the tier-to-model mapping is a set of profiles built and verified by a scheduled CI workflow and shipped with the release; the runtime only selects which profile applies.

## Consequences

From 1.7.0, native release checks run locally through installed Codex and Claude clients with existing logins. Publishing requires a manual Symphony CI dispatch on `main` with the exact locally reviewed and tested commit as `tested_sha`. CI rejects a different commit, repeats deterministic Linux and Windows checks, and publishes a new manifest version without provider client installs or AI API calls. The separate API-backed Capability refresh workflow is disabled for this release; its retained definition has an unconditional false job guard, including for manual dispatch. Restoring it requires a reviewed code change.

The persisted `capabilities` field is removed rather than left unwritten. On Claude Code it was worse than dead: the required model is compared against the model token parsed out of a packaged agent filename, so a snapshot naming any token without a matching agent file would block every lead spawn permanently, and the bad value was persisted into the recorded route so it survived retries. Deleting the field closes that hazard; a CI-generated agent-file set keeps the coupling satisfiable by construction.

Runtime still probes entitlement, but only to choose among pre-shipped profiles, never to learn model names. Codex reads its local model roster as a best-effort hint. On the first substantive Claude task, Symphony asks the same Claude Code login to serve minimal Sonnet 5 and Opus 5.5 requests. It disables hooks and MCP tools for the probe while retaining account and project settings, and accepts a model only when Claude Code's result names that exact model in `modelUsage`. Each request has a 15-second timeout and asks the CLI for a $0.25 budget, though loaded context can make actual usage exceed that limit before the CLI stops. Failed or inconclusive checks retain the Sonnet floor, and the attempt is cached for the session. Fable is never probed automatically because its use can require separate usage-credit consent. An explicit model list or profile pin skips these checks. No credential file is read by Symphony.

The refresh keeps the *published* map honest. It does not, and cannot, push anything to an installed copy. Neither host offers a marketplace entry that floats over the latest release tag: an entry pins a branch or tag by `ref`, a commit by `sha`, or a semver range only on an `npm` source. Auto-update for a third-party marketplace defaults to off on Claude Code, so a release reaches a user when they ask for it and not before. The maintainer's own Codex install sitting at 1.0.0 while the tree read 1.0.1 is what proved this, and it is why the workflow's job is described as keeping the map from rotting rather than as delivering anything.

The marketplace entry's `version` is therefore not a pin and never was. It is ignored at install time for every source type, because the plugin manifest wins. It is kept in sync anyway, because `claude plugin tag` refuses to tag a release when the two disagree.

## Lifecycle and cost policy (1.4.0)

Provider acceptance does not establish that a model is current or economical. `plugins/symphony/model-policy.json` records reviewed model lifecycle, capability bands and separate token-rate vectors, with official sources and a review date. Refresh agents receive this policy, and deterministic validation checks their choices against it. Unknown or non-current models cannot be selected. Newer adequate models take precedence; an older model needs lower verified rates to justify its selection. Generation is compared within a provider family, and capability is assessed separately from generation and price.

Codex uses Standard subscription credits per million tokens; Claude uses standard API dollars per million tokens, including cache reads and writes. These units describe different billing contexts and cannot be compared across providers or presented as plan allowance estimates. For a fixed token mix, the rate-weighted input/cache/output sum gives token cost. Reasoning effort changes token consumption without a fixed price multiplier, and retries, tools and context also affect cost. Choosing a lower rate therefore does not prove a lower cost per successful task. Future evaluation should use measured consumption and outcome quality where available.

The September 23, 2026 policy replaces GPT-5.5 routes with GPT-6 Luna. OpenAI's [Codex model documentation](https://learn.chatgpt.com/codex/models) schedules GPT-5.5's Codex retirement for October 14, 2026; its API lifecycle is separate. The [Codex rate card](https://learn.chatgpt.com/docs/pricing) lists Luna at 2.5 input, 0.25 cached-input and 12.5 output credits per million tokens, versus GPT-5.6 Sol's 100, 10 and 500. That makes Luna's token rates 40 times lower, while Sol remains a different capability class. An unknown roster uses the Luna floor. A known roster must include every model its profile selects: Luna+Sol accounts without Astra keep Luna for routine cells and use Sol for difficult cells, while a Sol-only profile covers accounts without Luna. A known roster that matches no profile blocks Symphony delegation with an explanation. Refresh preserves the model coverage of gated Codex fallback profiles.

Release CI checks the shipped matrix, its model references and policy consistency offline. Each provider block records the available model IDs used during generation, so CI checks newer alternatives against that roster without inventing availability or allowing the chosen matrix to hide a cheaper successor. The disabled capability-refresh workflow retains its live roster and model/effort verification path, including a policy-age limit of 45 days; it must not run under the current no-API release policy. Updating rates or adding a model requires reviewing the cited official sources and the capability/entitlement implications before advancing the date.
